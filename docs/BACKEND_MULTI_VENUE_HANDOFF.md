# arrive 다중 장소 지원 백엔드 인계

작성일: 2026-11-13
수신: Claude 백엔드 담당
상태: 구현 요구사항 정리 완료, 아래 추가 기능은 아직 미구현

arrive를 여러 방문 장소에서 사용할 수 있도록 장소 목록, 장소별 카탈로그, 방문별 카탈로그 버전 고정을 구현한다. 현재 동작하는 방문 공유 기능은 유지한다. 실제 제공할 장소는 우선 GIST 오룡관 한 곳이며, 두 번째 장소는 테스트용 데이터로만 검증한다.

이 문서는 다음 백엔드 작업의 기준이다. 기존 [초기 백엔드 인계](CLAUDE_BACKEND_HANDOFF.md)는 완료된 최초 구현의 기록이다. 이 문서의 API는 **추가 구현 명세**이며, 현재 배포된 API를 설명하는 것이 아니다.

## 1. 현재 구현과 필요한 변화

| 항목 | 현재 | 이번 작업 결과 |
|---|---|---|
| 장소 저장 | JSON 한 개를 읽는 `VenuesService` | 여러 장소와 각 장소의 여러 버전을 조회 |
| 장소 목록 | 없음 | `GET /v1/venues`로 현재 지원 장소 목록 반환 |
| 장소 상세 | `GET /v1/venues/:venueId` | 기존 응답 유지, 해당 장소의 현재 버전 반환 |
| 버전 지정 상세 | 없음 | 방문에 저장된 정확한 버전 조회 |
| 방문 생성 | `venueId`, `catalogVersion` 수신·저장 | 해당 조합의 카탈로그로 방문 생성 |
| 주차 후보 변경 | `this.venues.catalog`의 단일 목록 참조 | 세션의 장소·버전에 속한 주차 순서 사용 |
| Android | API 요청·응답 검사·상태 전이에서 `OryongDemo` 사용 | Codex가 선택한 장소 데이터로 변경 |
| 동승자 웹 | 장소의 현재 상세 조회 후 버전 일치 검사 | Codex가 세션 버전을 지정하여 조회하도록 변경 |

방문 생성·조회·이벤트·삭제, owner/share 권한 분리, 24시간 만료, 재시도 중복 방지, QR 공유와 웹 조회는 이미 구현되어 있다. 이번 요구사항 때문에 다시 만들 필요는 없다.

## 2. 작업 순서와 담당 범위

1. **Claude:** 장소 저장·조회 구조를 다중 장소/버전으로 확장한다.
2. **Claude:** 목록 및 버전 지정 상세 API를 추가하고 기존 세션 처리를 수정한다.
3. **Claude:** 계약·테스트·실행 문서를 갱신하고 Codex에게 결과를 전달한다.
4. **Codex:** Android 장소 선택, 카탈로그 저장·복원, 도메인 및 SDK 요청 위치를 연동한다. 동승자 웹도 정확한 버전을 조회하도록 바꾼다.
5. **공동 확인:** 오룡관 시연과 다중 장소·버전 테스트를 완료한다.
6. **별도 배포 단계:** HTTPS API와 동승자 웹을 배포하고 실제 휴대폰으로 시연한다.

Claude 작업 파일은 `backend/`, 관련 백엔드 배포 설정, `contracts/openapi.yaml`, 새 장소 인덱스/카탈로그 파일, 관련 문서다. API 계약은 이 문서 범위에 맞춰 갱신한다. Android의 `app/`, `domain/`, Gradle 설정 및 `companion/` 구현 변경은 Codex 담당이다.

기존 `contracts/oryong-demo.json`의 좌표·장소 ID·버전·미검증 표시는 보존한다. 원본 이미지나 실제 사용자 정보를 새로 만들지 않는다.

## 3. 장소와 버전 관리

### 최소 구현 방식

관리자 화면이나 장소 CRUD API는 이번 범위에서 만들지 않는다. 버전별 JSON 파일과 이를 묶는 명시적인 인덱스로 시작해도 된다. 장소 데이터를 DB로 옮기는 것은 필수가 아니다. 방문 세션의 기존 영속 저장은 유지한다.

인덱스에는 장소별 `venueId`, `currentVersion`, 버전별 파일 경로를 둔다. 예시 구조는 다음과 같다. 새 인덱스 위치를 `contracts/venues/index.json`으로 잡으면 경로는 인덱스 파일 기준으로 해석한다.

```json
{
  "venues": [
    {
      "venueId": "gist-oryong-demo",
      "currentVersion": "oryong-demo-v2",
      "versions": [
        {
          "catalogVersion": "oryong-demo-v2",
          "path": "../oryong-demo.json"
        }
      ]
    }
  ]
}
```

새 환경변수 `VENUE_CATALOG_INDEX_PATH`를 사용할 수 있다. 설정돼 있으면 인덱스를 읽고, 없으면 기존 `VENUE_CATALOG_PATH` 및 단일 파일 기본 경로를 유지하여 한 장소 목록으로 변환한다. 설정한 인덱스가 잘못됐을 때 단일 파일로 조용히 우회하지 않는다. Docker 이미지에는 인덱스와 참조한 파일이 함께 포함되어야 한다.

### 필수 규칙

- 식별자는 `(venueId, catalogVersion)` 조합이다. 같은 버전 문자열을 다른 장소가 사용해도 서로 섞이지 않아야 한다.
- `currentVersion`은 버전 문자열 정렬로 추측하지 않고 인덱스에서 명시한다.
- 같은 장소·버전의 중복 등록, 현재 버전 누락, 인덱스와 파일의 식별자 불일치는 시작 시 오류로 처리한다.
- 파일 경로는 관리자가 작성한 인덱스에서만 가져온다. 요청의 장소 ID나 버전 문자열을 파일 경로로 직접 사용하지 않는다.
- 좌표가 있으면 유한한 숫자와 위도/경도 범위를 검사한다. 한 카탈로그 안의 지점 ID도 중복되지 않아야 한다.
- **공개한 버전의 내용은 불변으로 운영한다.** 이름·주차 순서·만남 장소·좌표·검증 상태를 바꾸려면 새 버전을 추가한다. 이번 단계에서는 과거 버전을 자동 삭제하지 않는다.
- 등록된 과거 버전도 상세 조회와 방문 생성에 사용할 수 있다. 목록은 각 장소의 현재 버전만 노출한다.
- 서버 재시작·배포 후에도 진행 중인 방문이 참조하는 버전 파일을 보존한다.
- 미검증 좌표가 존재한다는 이유로 `DEMO_UNVERIFIED`를 `VERIFIED`로 변경하지 않는다.

## 4. API 추가 명세

기존 `/v1` 경로와 세션 응답 형식을 유지하는 추가 방식으로 구현한다. OpenAPI와 Swagger, 테스트가 같은 명세를 설명해야 한다. 브랜드 표기는 `arrive`로 맞춘다.

### 4.1 지원 장소 목록

`GET /v1/venues` — 인증 없이 조회, 성공 시 `200`.

```json
{
  "items": [
    {
      "venueId": "gist-oryong-demo",
      "catalogVersion": "oryong-demo-v2",
      "name": "GIST 오룡관",
      "verification": "DEMO_UNVERIFIED"
    }
  ]
}
```

- 위 네 필드를 필수로 하는 `VenueSummary`와 목록 응답 스키마를 계약에 추가한다.
- 한 장소당 현재 버전 한 항목만 반환한다. 순서는 인덱스 등록 순서로 고정한다.
- 장소가 없으면 `200 {"items": []}`를 반환한다.
- 목록에 없는 장소를 지원하는 것처럼 표시하지 않는다. 초기 실제 목록은 오룡관 한 곳이다.
- 현재 규모에서는 페이지네이션·거리순·위치 검색·검색어 필터는 제외한다.

### 4.2 현재 장소 상세

`GET /v1/venues/:venueId` — 기존 경로와 `Venue` 응답 형식을 유지한다.

해당 장소의 `currentVersion`을 반환하고, 없는 장소는 기존 오류 형식의 `404 NOT_FOUND`로 응답한다. 이 경로는 새 방문을 준비할 때 사용한다. 이미 생성한 방문의 버전을 복원할 때는 다음 경로를 사용한다.

### 4.3 특정 버전 상세

`GET /v1/venues/:venueId/versions/:catalogVersion` — 인증 없이 조회.

- 성공 시 `200`, 기존 `Venue` 스키마 그대로 반환한다.
- 존재하지 않는 장소 또는 버전 조합은 `404 NOT_FOUND`.
- 요청한 버전이 없으면 최신 버전으로 대체하지 않는다.
- 응답의 `venueId`와 `catalogVersion`은 요청한 조합과 정확히 일치해야 한다.
- 세션 토큰을 쿼리나 경로에 넣지 않는다. 장소 카탈로그만 공개 조회한다.

### 4.4 기존 방문 API

`POST /v1/sessions`의 요청 필드는 그대로 유지한다.

```json
{
  "venueId": "gist-oryong-demo",
  "catalogVersion": "oryong-demo-v2"
}
```

| 상황 | 결과 |
|---|---|
| 등록된 장소·버전 | 해당 버전으로 생성, `201` |
| 없는 장소 | `404 NOT_FOUND` |
| 알려진 장소의 없는 버전 | 기존 의미를 유지하여 `400 INVALID_REQUEST` |
| 같은 생성 키·같은 본문 재요청 | 기존 멱등 응답 유지 |
| 같은 생성 키로 장소나 버전 변경 | 기존 `409 IDEMPOTENCY_CONFLICT` |

첫 주차 후보, 만남 지점, `dataMode`는 모두 요청한 버전에서 결정한다. 현재 버전이 바뀌어도 기존 세션의 `venueId`, `catalogVersion`, `meetingPointId`, `dataMode`를 변경하지 않는다.

이벤트 처리에서는 `this.venues.catalog` 참조를 제거하고 세션의 `(venueId, catalogVersion)`으로 카탈로그를 조회한다. 주차 후보 제외·다음 후보 선택에는 그 버전의 주차 순서만 사용한다. 인증·만료 검사, 멱등 응답 재생, revision 비교와 원자적 갱신의 기존 동작을 보존한다.

진행 중인 세션이 참조하는 카탈로그가 운영 실수로 사라졌다면 최신 버전으로 대체하지 않는다. 이벤트를 적용하지 않고 `500 CATALOG_UNAVAILABLE`과 일반적인 안내 메시지를 반환한다. revision과 방문 상태는 그대로 둔다. 상세 조회는 해당 조합의 `404`를 반환한다. 이 오류와 복구 절차도 계약/문서에 기록한다.

## 5. 방문 버전 고정 예시

1. 장소 A의 v1에 주차 후보가 `P1 → P2`, 만남 지점이 `M1`로 등록되어 있다.
2. 방문 S1을 A/v1로 생성한다.
3. A/v2를 추가하고 현재 버전으로 지정한다. v2의 주차 후보는 `P3 → P4`, 만남 지점은 `M2`다.
4. S1에서 `REJECT_PARKING`을 보내면 다음 후보는 **P2**, 만남 장소는 **M1**이다.
5. 동승자 웹은 A/v1 상세를 조회하여 S1과 같은 안내를 표시한다.
6. 목록에서 A/v2를 선택해 만든 새 방문 S2에는 **P3**, **M2**가 적용된다.
7. 서버를 재시작해도 S1과 S2의 결과가 유지된다.

이 예시의 A/v1/v2는 테스트 fixture다. 실제 지원 장소나 검증된 좌표로 노출하지 않는다.

## 6. Codex가 함께 변경할 부분

| 영역 | 필요한 변경 |
|---|---|
| Android 장소 선택 | 목록 조회 → 장소 선택 → 상세 조회 → 해당 장소·버전으로 방문 준비 |
| `SessionApi.kt` | 생성 요청과 응답 검사의 `OryongDemo` 고정값 제거 |
| `VisitPlace.kt`, 장소 화면 | 선택한 카탈로그의 이름·하차·주차·만남 지점 표시 |
| `Trip.kt`, 방문 reducer | 기본 주차/만남 지점과 다음 후보를 전달받은 카탈로그에서 계산 |
| 로컬 저장·재전송 | 장소 ID·버전·해당 카탈로그를 방문과 함께 저장, 복원 시 조합 일치 검사 |
| SDK 요청 | 선택한 장소의 해당 버전 좌표 사용, 기존 추정 위치/에뮬레이터 제한 유지 |
| 동승자 웹 `app.js` | 세션의 장소·버전으로 특정 버전 상세 조회 |
| 동승자 웹 `server.mjs` | 읽기 전용 허용 경로에 버전 상세 추가. 현행 쿼리 차단·owner 경로 차단 유지 |

현재 APK는 오룡관 카탈로그를 포함하고 있으며 응답 버전도 고정 검사한다. 백엔드 작업만으로 앱의 범용 장소 선택이 완성되는 것은 아니다.

새 앱에서 장소 변경은 진행 중 방문을 조용히 덮어쓰지 않고 새 방문 준비로 처리한다. 기존 공유 링크 폐기와 미전송 변경 처리는 앱에서 명시적으로 정리한다. 다른 장소의 오프라인 변경을 새 방문에 섞어 전송하지 않는다.

## 7. 기존 앱과 배포 호환 순서

1. 백엔드에 새 조회 기능을 추가하되 실제 목록과 현재 버전은 기존 오룡관 v2로 유지한다.
2. 기존 APK와 웹으로 생성·주차 변경·공유 조회가 계속 동작하는지 확인한다.
3. Codex가 새 API를 사용하는 앱과 웹을 연결한다. 웹 프록시의 새 경로 허용도 이 단계에서 반영한다.
4. 테스트 환경에서 두 장소와 버전 변경을 검증한다.
5. 클라이언트 갱신이 끝난 뒤 실제 새 장소나 새 현재 버전을 활성화한다.

구형 웹은 현재 장소 상세만 읽기 때문에 서버의 현재 버전부터 바꾸면 기존 방문과 버전이 달라져 안내를 표시하지 못할 수 있다. 과거 버전 파일 보존과 클라이언트 갱신 순서를 함께 지킨다.

외부 배포는 기능 구현과 분리한다. 배포 단계에는 영속 PostgreSQL, HTTPS API 주소, 동승자 Node 웹의 HTTPS 주소, `API_BASE_URL` 연결, 카탈로그 파일 포함, 재시작 후 세션 유지 확인이 필요하다. Android의 공개 주소 두 개를 바꾸고 APK도 다시 빌드한다.

이번 단계에서는 백엔드 인스턴스 하나를 전제로 한다. 현재 트랜잭션 대기열과 요청 제한은 프로세스 내부에 있으므로, 여러 인스턴스를 운영하려면 DB 동시성 제어와 공유 요청 제한 저장소를 별도 작업으로 추가해야 한다.

## 8. 완료 기준

- [ ] 실제 목록은 오룡관 한 곳만 반환하고, 검증되지 않은 두 번째 실장소는 추가하지 않는다.
- [ ] 목록의 필수 필드·고정 순서·빈 목록과 상세/버전 조회의 오류를 검증한다.
- [ ] 서로 다른 두 테스트 장소에서 방문을 생성하고, 각 장소의 주차 순서와 만남 지점이 섞이지 않는다.
- [ ] 동일 버전 문자열을 두 장소가 사용해도 정확한 조합으로 조회한다.
- [ ] v1 방문 진행 중 v2를 현재 버전으로 바꿔도 기존 방문은 v1을 유지한다. 재시작 후에도 동일하다.
- [ ] 등록된 과거 버전으로 방문 생성 가능, 없는 장소/버전은 명세대로 거부한다.
- [ ] 잘못된 인덱스, 중복 식별자, 범위를 벗어난 좌표를 시작 시 거부한다.
- [ ] 버전 누락 시 다른 카탈로그로 전환하거나 이벤트 revision을 증가시키지 않는다.
- [ ] `DEMO_UNVERIFIED`의 세션은 `DEMO`를 유지한다.
- [ ] 기존 인증, 공유 토큰 쓰기 거부, 24시간 만료, 링크 삭제, 재시도 중복 방지, 충돌 처리 테스트가 계속 통과한다.
- [ ] 기존 테스트와 신규 단위/HTTP 통합 테스트, TypeScript 빌드를 통과한다.
- [ ] OpenAPI·Swagger·백엔드 README·환경변수 예시·Docker 카탈로그 포함 설정이 일치한다.
- [ ] 기존 APK·웹의 오룡관 v2 흐름을 유지하고 Codex가 연동할 API 예시를 전달한다.

## 9. 이번 범위에서 제외

회원가입, 결제, 푸시, WebSocket, 실시간 위치 추적, 빈 주차면 수집, 만차 예측, 장소 관리자 화면, 지도 검색 API 연동은 제외한다. 목록 확장은 안내 데이터를 준비한 장소를 제공하기 위한 작업이며 임의의 목적지에 대한 자동 경로 생성 기능은 아니다.

## 10. Claude 결과 전달 항목

- 변경 파일과 API 계약 차이.
- 목록/현재 상세/버전 지정 상세의 실제 응답 예시.
- 인덱스 작성법, 환경변수 우선순위, 구버전 보존 방법.
- DB 변경 여부와 필요한 마이그레이션. 불필요하면 없음을 명시.
- 실행한 테스트 명령과 결과, 미검증 항목.
- Codex가 앱과 웹 연동을 시작할 수 있는 서버 주소 또는 로컬 실행 방법.
- 배포용 파일 수정 여부와 실제 배포 여부를 구분해 기록.

작업을 시작할 때 기존 환경변수의 비밀값을 출력하거나 문서에 복사하지 않는다. 테스트는 별도 테스트 DB에서 실행한다. 실제 배포·시크릿 변경은 후속 배포 작업에서 진행한다.
