# arrive 전체 흐름 시연 점검 · 2026-11-14

## 후속 개선 상태

이 문서는 개선 전 시연 기록이다. 1번은 활성 방문 관측 + 알림함 복귀로 개선했고 Pleos 에뮬레이터에서 재검증했다. 2번은 차량 QR/휴대폰 입구 안내/합류 확인을 구현해 모의 API로 검증했으며 실제 백엔드 배포는 대기 중이다. 최신 적용 순서와 한계는 [CONTINUITY_SETUP.md](CONTINUITY_SETUP.md), 확정 API는 [CLAUDE_CONTINUITY_BACKEND.md](CLAUDE_CONTINUITY_BACKEND.md)를 참고한다.

## 결론

새 방문 생성 → QR 연결 → 하차 → 대체 주차장 선택 → 주차 → 합류 완료의 **단계 저장과 운전자/동승자 동기화는 확인했다.** 그러나 실제 사용자는 내비게이션에서 앱으로 돌아와야 하고, 차에서 내린 뒤에도 차량 화면에서 합류를 확인해야 한다. 따라서 자연스러운 사용 흐름까지 완성됐다고 볼 수는 없다.

이번 점검에서는 앱 코드를 변경하지 않았다. 이전 단위 기능 검사에서 직접 앱을 다시 열었던 부분을 실제 앱 전환 과정으로 점검했고, 그 과정에서 아래 문제가 드러났다.

## 검증 환경과 한계

- 설치된 Android debug 앱, Pleos Connect 2.1.0 에뮬레이터, 실제 `arrive.ikjun.com` / `arrive-api.ikjun.com` 배포 환경.
- 동승자는 Chromium 390 × 844 화면으로 확인했다. 실제 휴대폰 카메라 스캔 대신 차량에 표시된 QR을 해독해 동일 링크를 열었다. 실물 휴대폰 지도 앱 전환은 검증하지 않았다.
- 차량은 P 상태, 가상 GPS로 하차 지점과 주차장 좌표를 입력했다. 실차 주행·현장 보행·실제 사람의 하차/합류를 검증한 것은 아니다.
- 기존 방문의 암호화된 설정을 별도로 보존한 뒤 새 시연용 공유 방문을 생성했다. 기존 방문 링크를 사용해 상태를 바꾸지 않았다.
- 앱 복귀 단절을 확인한 후 나머지 상태 검증에서는 arrive를 직접 다시 열어 진행했다. 이 수동 복귀를 자동화 성공으로 계산하지 않았다.

| 단계 | 실제 관찰 | 판정 |
| --- | --- | --- |
| 공유 전 웹 | QR 또는 공유 링크가 필요하다는 안내 표시 | 정상 |
| 차량에서 QR 생성 | 입구 안내 공유 → QR 만들기 → 동승자 웹 연결 | 정상. 연결 준비가 방문 시작과 별개임 |
| 방문 시작 | 한 번의 클릭으로 하차 목적지 길안내와 웹 TO_DROPOFF 반영 | 상태 연동 정상. 내비 앱이 앞에 열림 |
| 하차 지점 접근 | 내비 화면에 머물면 arrive의 위치 관측이 중단됨. arrive 재진입 후 근처 안내/P 유지 확인 | 사용 흐름 보완 필요 |
| 하차 확인 | 주차장 1 길안내 요청, 웹에 ‘운전자는 주차 중이에요’ 표시 | 정상 |
| 주차장 변경 | 다른 주차장 선택 후 P2 및 주차장 2로 웹 반영 | 정상 |
| 주차장 2에서 P 유지 | ‘주차장 근처에서 P 확인. 주차를 마쳤나요?’ 표시 | 앱이 앞에 있을 때 정상 |
| 주차 완료 | 차량은 남측 입구 안내/합류 완료 버튼, 웹은 ‘주차를 마쳤어요’로 전환 | 데이터 정상. 차에서 내린 뒤 연결 단절 |
| 합류 완료 | 차량 버튼으로 확인하면 양쪽에 ‘함께 도착했어요’ 표시 | 상태 연동 정상. 실제 확인 위치가 부적절 |
| 동승자 인터넷 끊김 | 마지막 화면 유지 + ‘연결 끊김 · 마지막으로 확인한 상태예요’ | 정상 |
| 동승자 인터넷 복구 | 수동 새로고침 없이 최신 확인 표시로 복구 | 정상 |
| 웹 새로고침 | 같은 탭에서 QR 재스캔 없이 완료 방문 복원 | 정상 |

브라우저에서 확인한 오류 3건은 의도적으로 연결을 끊었을 때의 `ERR_INTERNET_DISCONNECTED` 요청이었다. 그 외 JavaScript 오류는 관찰하지 않았다. 각 단계는 정기 조회로 갱신하므로 운전자 버튼 직후 동승자 화면이 즉시 바뀌지는 않는다. 이번 점검으로 정밀한 지연 수치를 측정하지는 않았다.

## 개선 우선순위와 완료 기준

### 1. 내비게이션과 arrive 사이의 복귀 흐름 — 가장 먼저

**문제:** NaviHelper 경로 요청 뒤 내비게이션이 전면에 뜬다. 기본 뒤로 가기만으로 arrive에 돌아오지 않았고, 앱 목록을 통한 수동 복귀가 필요했다. `MainActivity.onStop()`에서 위치 관측을 중단하므로, 실제 내비 화면에서는 하차/주차 도착 제안을 받을 수 없다. 복귀하면 새 관측으로 P 유지 시간을 다시 채워야 한다.

**보완 방향:** 진행 중인 방문으로 돌아오는 명확한 진입점을 먼저 제공한다. 도착 감지를 내비 사용 중에도 유지하려면 Pleos 지원 범위와 Android 실행·알림 정책을 확인한 뒤 활성 방문 동안에만 지속되는 관측 수명을 설계한다. 임의로 화면을 강제 전환하는 방식은 피한다. 지원이 확인되기 전에는 ‘앱이 열려 있을 때 도착 확인을 돕는다’고 범위를 명확히 표시한다.

**완료 기준:** 사용자가 내비 화면에 머문 상태로 도착해도 다음 확인을 어디에서 해야 하는지 알 수 있고, arrive로 돌아온 뒤 중복 경로 요청이나 단계 초기화가 없어야 한다. 이 조건을 실제 에뮬레이터 앱 전환으로 재검증한다.

**백엔드:** 우선 앱의 수명/복귀 UI 문제. 기존 단계 API 변경 불필요.

### 2. 주차 뒤 휴대폰으로 이어가기와 합류 확인

**문제:** 주차 후 운전자가 건물로 이동해야 하는데 ‘합류 완료’는 차량 화면에만 있다. 실제 합류 전 미리 누르거나 차량으로 돌아와야 한다. 동승자 웹은 읽기 전용이라 현장에서 완료할 방법이 없다.

**보완 방향:** 주차 완료 시 운전자 휴대폰으로 입구 안내를 이어받고, 실제 만난 뒤 휴대폰에서 합류를 확인한다. 최소 범위로는 동승자 웹에 한정된 합류 확인 기능을 검토할 수 있다. 건물 내부의 정확한 만남 장소나 동승자의 입장 여부는 현재 공유하지 않으므로 이를 임의로 알고 있다고 표현하지 않는다.

**완료 기준:** 주차 이후 차량을 다시 만지지 않고 입구 안내 확인과 합류 완료를 끝낼 수 있어야 한다. 중복 확인·오프라인 재시도도 한 번의 완료 이벤트로 처리되어야 한다.

**백엔드:** 모바일에서 완료시키려면 변경 필요. 현재 공유 토큰은 조회 전용이며 이를 그대로 모든 운전자 쓰기 작업에 허용하면 안 된다. 참여자에게 허용할 좁은 동작, 인증/권한, 허용 단계, 중복 요청 처리를 합의한 뒤 구현한다. 구체적인 API 경로는 아직 확정하지 않았다.

### 3. 동승자 입구 안내를 실제로 따라갈 수 있게 만들기

**문제:** 기본 화면은 입구 핀과 ‘남측 광장 쪽 입구’를 보여준다. 상세를 열어도 ‘주변 보행 공간 확인 → 남측 광장 이동’ 수준이며, 어느 쪽 길로 돌아갈지 알려주는 검증된 경로나 출입구 사진이 없다. 현재 큰 CTA는 외부 지도에서 **입구 핀을 보는 링크**이고, 앱 내부의 검증된 보행 길안내가 아니다.

**보완 방향:** 실제 입구 사진 1~2장, 하차 지점에서 입구까지의 보행 동선과 눈에 띄는 지점 2~3개를 확인한다. 이를 한 문장 다음 행동과 지도에 반영한다. 동승자 위치 표시가 필요하면 별도 선택적 위치 동의를 받되, 검증되지 않은 직선을 보행 경로처럼 표시하지 않는다.

**완료 기준:** 처음 온 사람이 추가 설명 없이 지정 하차 지점에서 실제 입구까지 갈 수 있어야 한다. 현재 지도/문구만으로 이 조건을 충족했다고 판단할 근거는 없다.

**사용자 확인 필요:** 남측 입구 사진, 북측 하차 지점에서 어느 쪽으로 돌아가는지, 통행 가능한 보행로와 문 위치. 기존 남측 광장 방향 확인만으로 실제 경로가 검증된 것은 아니다.

**백엔드:** 현재 안내 JSON의 사진/설명 보강은 기존 구조로 가능. 경로 geometry나 새로운 검증 메타데이터를 추가하면 카탈로그 계약 확장이 필요할 수 있다.

### 4. 시연 위치 설정과 완료 화면 정리

- arrive의 가상 GPS는 GIST로 옮겼지만 내비 앱은 수정구 시흥동에서 오룡관까지 약 270km 경로를 표시했다. **두 화면의 위치 입력이 일치하지 않는 것을 관찰했다.** 원인은 아직 특정하지 않았으므로 앱 경로 계산 오류나 특정 SDK 설정 문제로 단정하지 않는다. 발표 전 내비 시작 위치까지 맞추거나, 길안내 연동 검증과 캠퍼스 도착 상황 재생을 구분해 보여줘야 한다.
- 합류 완료 후에도 동승자 화면의 가장 큰 제목/버튼은 입구 안내다. 완료 상태를 중심으로 바꾸고 입구·주차 정보는 다시 볼 수 있는 보조 항목으로 내리는 것이 자연스럽다.
- QR 준비와 방문 시작이 분리돼 있다. 처음 이용할 때 ‘동승자 연결 후 출발’ 흐름을 분명히 하되, 동승자가 없는 방문을 막지는 않는 구성이 필요하다.

## 조작 수에 대한 해석

최소 앱 내부 조작만 세면 공유 3회(공유 열기/QR 만들기/닫기) + 기본 진행 4회(시작/하차/주차/합류)다. 주차장 변경은 추가 조작이다. **내비 화면에서 앱으로 복귀하는 조작, 권한 허용, 동승자의 QR 스캔/상세 열기는 이 수에 포함되지 않는다.** 따라서 ‘전체 흐름이 4번의 터치로 끝난다’고 설명하면 안 된다. 특히 합류 확인의 위치부터 바꿔야 현실적인 조작 수를 평가할 수 있다.
